      CLI commands

      Eight commands cover the lifecycle standalone via sf-lwc <command> (or npx sf-lwc). Six core commands (add, diff, doctor, list, pack, update) are also available natively inside Salesforce CLI via sf lwc <command>.

      sf-lwc init

      Writes the default registry spec and workspace settings to sf-lwc.json so team installs run consistently.

      $sf-lwc init

      sf-lwc add [source] [component...]

      Installs components and companion Apex/labels, updating sf-lwc.lock.json. Specify an upstream repository (sf-lwc add owner/repo [component]) or omit the source to pull from your project's configured registry in sf-lwc.json (e.g. sf-lwc add dataTable). In an interactive terminal, omit component names to launch the multi-select picker.

      $sf-lwc add dataTable

      sf-lwc list [source]

      Lists available components from a remote GitHub repository or local SFDX project without touching GitHub REST API quota. Omit source to query the project's configured registry. (Alias: ls)

      $sf-lwc list

      sf-lwc diff <component>

      Displays a unified, line-by-line colored diff between your local customized copy and the upstream registry version.

      $sf-lwc diff dataTable

      sf-lwc update [component...]

      Compares lockfile versions with upstream registry, then upgrades component files and Custom Labels (pass --all to upgrade all installed components).

      $sf-lwc update --all

      sf-lwc remove <component...>

      Removes an installed component and its files after verifying no other components depend on it (override with --force). (Alias: rm)

      $sf-lwc remove dataTable

      sf-lwc doctor

      Checks SFDX project root, configuration, registry reachability, lockfile integrity, and verifies that every tracked file exists on disk.

      $sf-lwc doctor

      sf-lwc pack <component>

      Queries the Salesforce Tooling API across Apex, Labels, and child LWCs, exporting into clean .sf-lwc/ sidecars. (Alias: export)

      $sf-lwc pack myComponent -o myOrg

      Common flags

      --dry-run Simulates operations and previews written files or merged labels without modifying disk
      -w, --overwrite Overwrites existing local component files during installation or update
      --force Bypasses dependency blocking checks on remove, or overwrites config in init
      --json Outputs machine-readable JSON for CI/CD runners and automated pipelines
      --from <repo> Overrides registry or source repository (supports owner/repo, branch refs, or local paths)
      -o, --target-org Target scratch org or sandbox username/alias for sf-lwc pack metadata discovery

      Architecture & key mechanics

      How sf-lwc works under the hood—from zero-quota tarball streaming to full-stack Salesforce DX metadata installs.

      01

      Zero-Rate-Limit Transport

      src/source.js

      GitHub unauthenticated REST APIs limit requests to 60 per hour per IP. When running behind corporate NATs or shared CI runners, that limit hits immediately and breaks installations.

      • Codeload tarball streaming: We bypass api.github.com entirely and fetch gzip tarballs directly from codeload.github.com/{owner}/{repo}/tar.gz/{ref} using Node 18 native fetch.
      • In-memory tar parsing: parseTar() unpacks files into an in-memory virtual map (_filesMap) after buffer decompression via zlib.gunzipSync(). We never hit disk or burn unauthenticated API quota.
      • Native Git fallback: If corporate proxies block codeload downloads, the runner drops back to git clone --depth 1 over HTTPS automatically.
      02

      Apex & Metadata Bundling

      src/install.js · src/labels.js

      Lightning Web Components rarely exist alone. Production components depend on Apex controllers, test classes, and Custom Labels. Standard package managers drop JS files and ignore Salesforce metadata.

      • DX project routing: The installer reads sfdx-project.json to find the default package directory, routing LWC files to lwc/<name>/ and Apex to classes/.
      • Non-destructive label merging: mergeLabels() inspects CustomLabels.labels-meta.xml, skips existing <fullName> entries, and appends new labels right before </CustomLabels> without rewriting or reformatting existing tags.
      • Lockfile tracking: Every installed file, version, label, and dependency is recorded in sf-lwc.lock.json for clean diffing and drift prevention.
      03

      Sidecar Manifests & Dependency Safety

      src/resolve.js · src/remove.js

      Components declare their metadata contracts in .sf-lwc/<name>.json sidecar manifests—companion JSON files storing component version, target API level, Apex companion classes, and Custom Labels without modifying Salesforce's native *-meta.xml descriptors. Keeping contracts in sidecars preserves native DX compatibility and zero-configuration deploys.

      • Unmanifested repository synthesis: When pulling from arbitrary GitHub repositories without .sf-lwc/ manifests, the resolver auto-discovers component bundles across the DX project tree dynamically.
      • Path traversal protection: safePath() validates all declared file paths. Leading slashes, Windows backslashes, and directory escapes (..) are rejected immediately before touching disk.
      • Dependency graph safety: If component A depends on component B, running sf-lwc remove B is blocked by findBlockingDependents() with an error showing what would break, unless overridden with --force.
      • Cycle detection: Recursive manifest resolution tracks visited nodes and stops cyclic dependency loops cleanly before writing to disk.
      04

      Live Org Reverse-Engineering

      src/pack.js

      The sf-lwc pack command lets you export components directly from an active Salesforce org or local DX project without manually writing manifests.

      • Tooling API graph introspection: Queries MetadataComponentDependency to discover companion Apex controllers, unit test classes, and custom label XML definitions.
      • Local mapping: Resolves discovered metadata dependencies through METADATA_REGISTRY to local package directory paths.
      • Manifest export: Generates a clean .sf-lwc/<name>.json sidecar with exact versions and file references, ready to share or commit to a registry.
      05

      Dual Distribution: Standalone CLI & Native sf Plugin

      bin/sf-lwc.js · packages/plugin-lwc

      Developers shouldn't need a heavy toolchain just to try a component, but teams already using Salesforce CLI expect native tooling integration.

      • Zero-install CLI: npx sf-lwc add <name> runs instantly in any workspace without global npm dependencies.
      • Official Salesforce CLI plugin: Six core commands (add, diff, doctor, list, pack, update) plug directly into sf (sf lwc add) via packages/plugin-lwc using @oclif/core and @salesforce/sf-plugins-core.
      • Shared core engine: Both binaries invoke the exact same core modules (src/) and interactive terminal UI (@clack/prompts), so flags, locks, and behaviors remain identical.

      Prerequisites & runtime architecture

      sf-lwc relies on standard Node.js APIs to keep installs fast and deterministic.

      Prerequisites

      • Node.js >= 18: Required for native util.parseArgs, web streams, and built-in test runner.
      • Salesforce DX Workspace: A project directory containing sfdx-project.json.
      • Git CLI (Optional): Auto-detected fallback if corporate firewalls restrict direct HTTPS tarball streaming.
      • Salesforce CLI (Optional): Only needed when using the native sf lwc plugin or packing live org metadata.

      Built-in Node.js APIs

      • node:util (parseArgs): Zero-dependency CLI option and argument parsing via Node's native util.parseArgs.
      • Node 18 fetch & node:zlib: Direct tarball downloading and in-memory gunzip buffer parsing without disk thrash.
      • node:test & node:assert: Native Node test runner driving the full test suite with zero test framework bloat.
      • node:fs/promises: Atomic lockfile writes, safe file reads, and path traversal verification.

      Platform & Tooling APIs

      • Tooling API Graph Queries: sf-lwc pack inspects MetadataComponentDependency to extract Apex classes, unit tests, and custom labels straight from an active scratch org or sandbox.
      • DX Package Directory Resolution: Auto-detects custom package directories defined in sfdx-project.json.
      • SLDS Scoped Architecture: Bundles pure SLDS styling with zero runtime framework wrappers or shadow DOM collisions.
